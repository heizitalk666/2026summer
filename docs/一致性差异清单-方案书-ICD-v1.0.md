## 0　用途与读法

这份清单是 **D3 评审的议程**，不是设计文档。每一条对应评审桌上的一次表决，第 7 节的决议表可当场勾填，会后直接作为 ICD 附录 C 变更记录的输入。

清单本身**不修改 ICD 正文，也不修改方案书**。取舍是全组决议，这里只提供决议所需的材料：两份文档的原文对照、推荐取舍及其理由、改动落到哪一节哪个字段、以及改动引起的数值连锁影响。

分类与优先级：

| 类别 | 含义 | 是否阻塞 D3 冻结 |
|---|---|---|
| **A** | 硬冲突。两份文档对同一件事给出互斥的设计，按现状冻结会导致一方的核心设计无法实现 | **阻塞**，必须在 D3 定 |
| **B** | 单侧缺失。一份文档有、另一份完全没有，且缺失方偏离了任务书要求 | 阻塞 B3；B1/B2/B4 可当场定 |
| **C** | 数值与口径不一致。设计意图相同，数字或说法对不上 | 不阻塞，但应一并改完 |
| **D** | ICD 自身的技术意见。与方案书无关，是 Schema 与校验设计上的改进建议 | 不阻塞 |

按 ICD 的冻结规则，改动成本差别很大，推荐取舍时已把成本计入：

| 改动类型 | 成本 |
|---|---|
| 新增可选字段、新增枚举值 | 次版本号 +1，通知即可 |
| 修改字段语义、类型、范围 | **主版本号 +1，全组重评审，三个桩同步改** |
| 增删白名单指令 | **需重新评审安全边界，默认不批准** |

## 2　A 类：硬冲突

### A1　云台 PID 视觉伺服在协议上没有通路

**现状对照**

| | 方案书 | ICD v1.0 |
|---|---|---|
| 控制量 | §6.3.1「控制量为云台方位角速度 ω，单位为度每秒」，位置式 PID，控制周期 T=100 ms | §4.1 白名单只有 `PTZ_SET`（设定**姿态**：`pan_deg`/`tilt_deg`/`zoom`/`speed`） |
| 增益调度 | §6.3.2　ω(k) = [θ/(W·z)]·u(k)，随变焦倍率折算 | 无对应字段 |
| 驱动接口 | §8.3.3 控制输出模块经网关转发至云台 | §8.4 `IPTZ` 只有 `set_pose()` / `home()` / `status()` / `poll()` / `close()`，**没有任何速率方法** |
| AIM 状态 | §6.4 第 4 步「云台 PID 闭环把目标调整至画面中心，稳态偏差 <20 px」 | §7.2 `AIM` = 下发**一次** `PTZ_SET(pan,tilt,zoom=1)`，等 `ptz.at_target = true` —— 属**开环指向** |

方案书 §2.3 把云台方位与俯仰称为「本课题控制算法设计的重点」，§9.1 第六级调试专门是 PID 整定，§9.3 有超调量 ≤10 %、调节时间 ≤1.5 s、稳态误差 ≤20 px 三项控制性能指标，§11.1 交付物里有「PID 整定记录、阶跃响应曲线」。这些在 ICD v1.0 下**全部无法产生**：开环指向没有超调，也没有阶跃响应曲线可画。

**推荐取舍：方案甲——在 `IPTZ` 与白名单增补受限的 PTZ 速率通路**

- 在 `IPTZ` 增补 `set_rate(pan_dps, tilt_dps, ttl_ms) -> ExecHandle`
- 白名单增补 `PTZ_RATE`，参数 `pan_dps` / `tilt_dps` / `ttl_ms`，网关硬编码范围建议 `pan_dps ∈ [-60, 60]`、`tilt_dps ∈ [-40, 40]`（取 `ptz_stub` 的 `pan_speed_dps`/`tilt_speed_dps` 默认值为上限）、`ttl_ms ∈ [100, 500]`

**理由**

1. **它不触碰任务书关心的那条安全边界。**任务书禁止的是「直接控制车辆转向、电机扭矩或制动力」。ICD §4.1 的白名单表自己有一列「是否改变车辆运动」，`PTZ_SET` 那一格填的就是**否**。云台已经由 AI 侧按位置全权控制，把控制量从"位置"换成"速率"，改变的是云台的控制形式，不是车辆的安全边界。§4.1 那句「协议中不存在转向角、轮速、扭矩、制动力、目标速度这类量」针对的是底盘，评审时需要把这个区分讲清楚，否则容易被误读成"任何速度量都不许有"。
2. **`ttl_ms` 是这条指令的安全兜底。**速率指令必须自失效：超过 `ttl_ms` 没有新指令刷新，云台自动归零速度。否则 `mission` 崩溃时云台会一直转到限位。这条由**网关**执行（网关本来就有看门狗计时），不依赖 AI 侧。加了它之后，`PTZ_RATE` 的最坏情况是"云台多转 500 ms × 60 °/s = 30°"，且不影响车辆。
3. **PID 的视觉反馈来自图像，闭环无法下沉到驱动层。**有人会提第三条路——把伺服环放进云台驱动内部，`mission` 只给目标位姿。这条走不通：反馈量是目标形心的像素坐标，只有 `perception` 有图像，云台驱动看不到画面。闭环必须经过 AI 侧，这也正是"视觉伺服"的定义。这条要在评审时主动说明，堵住这个方向的追问。

**备选方案乙——`PTZ_SET` 位置增量的多轮闭环**（不改白名单）

PID 照常算出 ω，再折算成位置增量下发：`pan_target(k) = pan_now + ω·T`。代价有三：

- `at_target` 语义被破坏——每 100 ms 覆写一次目标，`at_target` 永远是 `false`，而 ICD §7.2 的 `AIM` 与 §5.3 的 `CAPTURE` 前置条件都依赖它
- 指令流量从"事件驱动 + 5 Hz 心跳"涨到 10 Hz，每条都要走 REQ/REP 往返 + 五项校验 + 生成 `exec_handle` + 触发一条 `EXEC_UPDATE` 型 `StatusReport`
- `chassis_stub` 的 `ack_drop_rate = 0.02` 下，一次 15 轮的 AIM 有约 26 % 的概率丢掉至少一条指令，伺服环会卡顿

乙方案的好处是完全不动白名单，D3 上更容易通过。若评审对甲方案的安全影响仍有顾虑，乙是可接受的退路，但 `at_target` 的语义必须同步重定义。

**改动清单（甲方案）**

- ICD §4.1 白名单表：增一行 `PTZ_RATE`，「是否改变车辆运动」填**否**
- ICD §4.3 参数与网关校验范围表：增 `pan_dps` / `tilt_dps` / `ttl_ms` 三行
- ICD §7.2：`AIM` 行的「发出」改为 `PTZ_RATE` 闭环，「等待条件」改为像素偏差进入 ±20 px 带且保持
- ICD §8.4 `IPTZ`：增 `set_rate()` 抽象方法；`PTZCaps` 增 `max_pan_dps` / `max_tilt_dps`
- `control_command.schema.json`：`command` 枚举增 `PTZ_RATE`，`$defs` 增 `ptzRatePar`
- ICD §9.2 `ptz_stub`：按 `pan_speed_dps`/`tilt_speed_dps` 实现速率积分
- 方案书 §7.4：「四条任务级指令」的措辞同步改（见 C6）

**连锁影响**

`AIM` 预算 1.5 s 与方案书 §2.3 的「调节时间 ≤1.5 s」本来就一致，T_r 不变。但 ICD §10.2 评审 checklist 的「白名单六条指令」需改为七条，且「协议里确认不存在转向角、轮速、扭矩、制动力、目标速度」这一条要补一句说明：`PTZ_RATE` 的速率量作用于云台，不作用于底盘。

### A2　首版缺陷三类，两份文档选的不是同一组

**现状对照**

| | 方案书 §6.2.1 表 6-2 | ICD 附录 B.1 |
|---|---|---|
| 第一类 | 指针表读数 | `PRESSURE_GAUGE`（建议纳入） |
| 第二类 | 指示灯状态 | `INDICATOR_LIGHT`（建议纳入） |
| 第三类 | **开关分合位** | **`OIL_LEAK` 渗漏油**（建议纳入）；`SWITCH_HANDLE` 标为**二期** |

方案书 §6.2.1 有明确论证：「经检索，室内配电室的设备外观缺陷（**渗漏油**、呼吸器变色、积水）几乎没有公开可用的标注数据」，因此识别对象定为三类状态量。而 §2.4.5 把这条列为课题的硬约束（无法进入运行中配电室采集数据）。

ICD 选中的 `OIL_LEAK` 正是方案书论证过做不了的那一类；被 ICD 降为二期的 `SWITCH_HANDLE`，在方案书里是表 2-2 和表 11-2 的**正式验收指标**（开关分合位识别正确率 ≥99 %）。

**推荐取舍：以方案书为准，首版三类改为 `PRESSURE_GAUGE` / `INDICATOR_LIGHT` / `SWITCH_HANDLE`**

**理由**

1. 方案书这一侧有数据可得性论证和数据集出处（Roboflow `distribution_room`，2773 张，CC BY 4.0，三类标注同源不需域适配），ICD 这一侧没有。有论证的一方胜出。
2. 删掉 `SWITCH_HANDLE` 等于删掉一条已写进预期指标表的验收项。
3. ICD 挑选三类的依据是「一个走 L2 读数、一个走 L2 分类、一个走纯 L1 检测，三类各自打通一条链路」。换成开关分合位之后，三类里有两类走 L2 分类（`INDICATOR_LIGHT` 与 `SWITCH_POSITION` 都已在 `l2_reading.kind` 枚举里），**纯 L1 通路空出来了**。这个缺口正好由 B1 的 L3 异常检测补上：EfficientAD 是非监督的，只用正常样本训练，**不需要缺陷标注数据**——恰恰绕开了那条卡死 `OIL_LEAK` 的约束。所以 A2 与 B1 应当合并决议：换掉 `OIL_LEAK`，同时把 L3 正式写进方案书，架构覆盖面不减反增。

**改动清单**

- ICD 附录 B.1：`OIL_LEAK` 的「首版是否纳入」由「建议纳入」改「二期」，`SWITCH_HANDLE` 反之
- ICD 附录 B.1 表下的说明段落：「一个走 L2 读数、一个走 L2 分类、一个走纯 L1 检测」改写为「两类走 L2 通路，纯 L1/未知异常通路由 L3 承担」
- 方案书 §6.2.1：无需改
- **`detection_event.schema.json` 不需要改**——ICD 附录 B.1 已写明「Schema 里的 `enum` 保留全部十类，收窄只在训练与验收层面执行」。这是 A 类里成本最低的一条，只改一张表的一列。

### A3　CAPTURE 语义不同：三视角 vs 连拍三帧

**现状对照**

| | 方案书 | ICD v1.0 |
|---|---|---|
| 采集什么 | §5.4「单次复核采集三个视角：主视角，以及左右各偏转 15° 的两个辅视角」，由同一台相机经云台转动依次获得 | §7.2 `CAPTURE`「3 帧抓取完成」；§8.5 `ICamera.grab_burst(n=3, interval_ms=150)`，**同一位姿** |
| 为什么 | §5.4 一是三视角一致性比对抑制反光与偶发遮挡造成的**误读**，二是主视角被高光覆盖时可用辅视角替代 | §6.1「云台停稳后仍有残余抖动，3 帧里挑最清晰的一帧送二级模型」，抗**运动模糊** |
| 耗时 | 0.5 s 稳定 + 0.2 s 采集，×3 = **2.1 s** | **0.6 s** |
| 下游用途 | §6.1.3「三个视角的读数极差若超过 0.5 % FS，判定本次测量不可信」——这是方案书对「前述滤波都无法处理的系统性误差」的**唯一兜底** | 三帧全部入包，「丢弃的两帧对分析复核失败原因有用」 |

两者解决的是**不同问题**，不是同一件事的两种写法，不能互相替代。ICD 里三视角一致性判定完全没有落点：`EvidencePackage` 的 `after` 只有一组读数，没有多视角极差字段。

**推荐取舍：两者都保留，但三视角改为条件式触发**

- 默认路径：`CAPTURE` 维持单视角连拍 3 帧，0.6 s，T_r 不变
- 条件路径：当质量评价判定主视角存在高光遮挡（接 A4 的 `highlight_ratio`），或首次读数的 `reading_confidence` 低于阈值时，追加左右各 ±15° 两个辅视角，`CAPTURE` 延长到 2.1 s，并做三视角一致性判定

**理由**

无条件三视角与只连拍不三视角，两个极端都有明确代价：

| 方案 | T_r | N_max | 代价 |
|---|---|---|---|
| 无条件三视角（方案书原样） | 10.3 s | **19** | 复核能力比 22 次降 14 %，而三视角真正有用的场合（镜面高光）只占少数 |
| 只连拍不三视角（ICD 原样） | 8.8 s | 22 | 方案书 §6.1.3 的系统性误差兜底被删，§6.1.5 的 0.65 % FS 误差分析随之失去最后一道防线 |
| **条件式（推荐）** | 均值≈8.8 s | ≈22 | 需要一个"何时追加辅视角"的判据——正好是 A4 要补的字段 |

方案书 §4.3.1 把「表盘玻璃镜面反射」列为本场景**最主要的光学干扰源**，并明确说本方案以「检测到高光遮挡时改变云台角度重新拍摄，从几何上避开反射角」为主要抑制手段。这条不能删；但它按定义就是条件触发的，无条件付 2.1 s 并不符合它自己的设计意图。

**改动清单**

- ICD §7.2：`CAPTURE` 行的「等待条件」改为「主视角 3 帧完成；若判定需辅视角，则三视角各 3 帧完成」，预算 0.6 s / 条件路径 2.1 s，超时相应由 1.5 s 放宽到 4.0 s（见 C1）
- ICD §6.1 目录结构：`verify_01..03.jpg` 的角色语义需区分主视角连拍帧与辅视角帧，建议新增文件名约定 `verify_aux_l.jpg` / `verify_aux_r.jpg`
- `evidence_package.schema.json`：`files[].role` 枚举增 `VERIFY_FRAME_AUX`（新增枚举值，次版本 +1）；`after` 建议增可选字段 `multiview_spread`（三视角读数极差，% FS）
- ICD §8.5 `ICamera`：**不改**，`grab_burst` 保留原语义
- ICD §9.2 `ptz_stub`：4K 裁剪仿真天然支持 ±15° 偏转，无需改实现，但标定素材需覆盖辅视角视场
- 方案书 §5.4 / §6.4 第 6 步：改为条件式

**连锁影响**

`EvidencePackage.timeline` 的 `state` 枚举不变；但 `duration_ms` 在 `CAPTURE` 上会呈双峰分布，统计复核耗时时要按是否走辅视角分组，否则均值没有意义（与 ICD §6.4 里 `delta_conf` 按 `verdict.result` 分组是同一类陷阱）。

### A4　图像质量评价（质量总分 Q）在接口上消失

**现状对照**

| | 方案书 | ICD v1.0 |
|---|---|---|
| 触发条件 | §6.4 第 2 步「质量总分低于 0.75 且变焦未达上限时，判定需要主动测量」；第 1 步「对每个目标计算**像素密度等四项质量指标**」 | §3.3 五条 `trigger_rule`：`CONF_BAND` / `L2_UNREADABLE` / `L2_OUT_OF_BAND` / `L3_ANOMALY` / `MANUAL` |
| 字段 | — | `DetectionEvent` 中 **`quality_score` 出现 0 次**，无任何质量指标字段 |

另有一个方案书自身的问题：「四项质量指标」在全文出现两次（§6.4 与 §8.2 伪代码），**从未列出是哪四项**，只写了"像素密度等四项"。评审时一定会被问到。

任务书把「目标检测、已知缺陷识别、未知异常检测和**图像质量评价**」并列为主要研究内容，并把「拍摄质量不达标时主动补拍」写进预期成果的闭环定义里。这条不能就这么消失。

**推荐取舍：`trigger_rule` 保留不动，另在 `detections[]` 增补 `quality` 可选对象，把四项指标显式化**

建议的四项：

| 字段 | 含义 | 已有替代 |
|---|---|---|
| `pixel_density_px` | 空间采样密度 | 已有同名顶层字段，`quality` 内引用即可不重复 |
| `blur_score` | 清晰度 / 运动模糊，0–1 | 无 |
| `highlight_ratio` | ROI 内过曝像素占比，0–1 | 无——**A3 的条件式辅视角就靠它触发** |
| `occlusion_ratio` | 遮挡或截断比例，0–1 | 无 |
| `score` | 加权总分，即方案书的 Q | 无 |

同时在 `trigger_rule` 枚举增一条 `QUALITY_LOW`（`score < 0.75` 且变焦未达上限）。

**理由**

1. 两者本不冲突：`L2_UNREADABLE`（`pixel_density_px < 120`）本来就是四项里最重要的一项，ICD 只是把最重要的那项单独提成了枚举，把其余三项丢了。补回来就是。
2. 补上之后，A3 的条件式三视角有了机器可读的判据，答辩时「怎么判断拍摄质量不达标」有具体字段可指，而不是一句"加权得 Q"。
3. **成本最低**：按 ICD 冻结规则，新增可选字段与新增枚举值都只需次版本号 +1，通知即可，不用全组重评审、不用改桩。四条 A 类里只有这一条不动主版本号。

**改动清单**

- `detection_event.schema.json`：`detections[].properties` 增 `quality` 对象；**必须放在 `required` 之外**——`detections[]` 的 `additionalProperties` 是 `false` 且 `required` 列全了所有字段，若把 `quality` 设为必填，已写好的桩与示例报文会全部失效
- ICD §3.1 字段表、§3.3 触发判据表、附录 B.4 `trigger_rule` 行同步
- 方案书 §6.4：把「四项质量指标」按上表列明
- ICD §10.1 反例：可增一条「`quality.score` 越界」

**C4**　推荐方案书的按需变焦。固定 `zoom=3` 对近距离目标会过度放大导致目标出框——方案书 §9.4 的问题预案里「变焦后目标丢失」写的就是这个，处理方向是「先居中再变焦；变焦分两步执行并中途校正」。ICD 的 `AIM`→`ZOOM` 拆分已经落实了"先居中再变焦"，但固定 3× 没有落实"按需"。连锁：ZOOM 预算 1.2→1.5 s，T_r 8.8→9.1 s，N_max 22→21。

**C5**　这是唯一会推翻已冻结数值的一条，单列在第 6 节。**方案书内部先要自洽**：§3.4 选型表写 60°–20°，§4.1.3 由自己给的 f 与 w 算出 67°–25°，两处对不上。推荐做法是暂按 60° 冻结（两份文档现状一致，改动最小），同时在 ICD §9.2.3 像素密度标定里加一条硬性条款：**实测 θ 与 60° 偏差超过 3° 时，d_max 与路线标定规范必须按实测值重算并通报全组**。第 6 节给出 67° 情形的完整重算，让评审知道风险敞口有多大。

## 5　D 类：ICD 自身的技术意见

以下五条与方案书无关，是 Schema 与校验设计上的问题。**每一条都已用 `jsonschema` 实测验证过**，不是纸面推断。

### D1　`brake_latency_ms` 的 `maximum: 100` 把验收指标焊进了实测值的线格式

`status_report.schema.json` 里 `brake_latency_ms` 写的是 `{"type":["integer","null"],"minimum":0,"maximum":100}`，§10.1 还拿 `brake_latency_ms = 150` 当第 7 条反例。

问题在于这是一个**实测值**，不是一个指令参数。ICD §5.8 自己说得很清楚：「`StatusReport` 里的 `brake_latency_ms` 是底盘报上来的实测值，作用是让这条指标**可验收**」。实测验证：构造一条 `brake_latency_ms = 150` 的 `StatusReport`，**整条报文被判非法**。也就是说真机哪天制动慢到 150 ms，系统拿到的不是"一条记录着超标的报文"，而是一条解析失败的报文——恰好把"指标被违反"这个最该留证的证据丢掉了，而这正是这个字段存在的唯一理由。

**建议**：Schema 上限放宽（如 `maximum: 5000`），超过 100 ms 由网关判逻辑并抛 `SafetyEvent`。§10.1 第 7 条反例改为「`brake_latency_ms = -1`」或换成别的约束。

### D2　`command_ack` 缺 `PREEMPTED` 分支

`allOf` 里只对 `result = ACCEPTED` 和 `REJECTED` 写了 if/then。实测验证：构造一条 `result = "PREEMPTED"` 且同时带 `reject_code` 和 `exec_handle` 的 ACK，**Schema 放行**。

ICD §4.4 说 `PREEMPTED` 表示指令被更高优先级动作打断，语义上不应带 `reject_code`。**建议**增第三条 if/then：`PREEMPTED` 时 `reject_code` 为 `null`、`exec_handle` 为 `string`。

### D3　`evidence_package` 的 `l2_reading` 退化，丢掉了内部校验

`$defs.snapshot` 里 `l2_reading` 只写了 `{"type":["object","null"]}`，而 `detection_event.schema.json` 里同名结构有完整的 8 个字段、`kind` 枚举和 `additionalProperties: false`。实测验证：往 `after.l2_reading` 塞一个 `{"kind":"NO_SUCH_KIND","junk":1}`，**Schema 放行**。

证据包是要写进台账、回流训练集的最终产物，它的读数结构反而比中间报文校验更松，方向反了。**建议**用 `$ref` 复用 `detection_event.schema.json` 的定义（Draft 2020-12 支持跨文件 `$ref`，两份 Schema 都有 `$id`）。

### D4　§10.1 第 6 项「逐字节一致」过脆

「比对附录 D 内嵌的 Schema 与 `schemas/` 下的文件是否**逐字节**一致」——markdown 围栏的缩进、行尾换行、编辑器的尾随空白都会让它误报，而这类误报会训练出"红了就手工改一下附录"的习惯，反而削弱这条检查。**建议**改为 `json.loads` 后深比较，语义一致即可。

### D5　网关硬编码范围与 Schema 范围是两份真值，ICD 没说清谁说了算

ICD §4.3 强调「下表右侧两列是**网关进程内硬编码的常量**……网关不从 AI 侧下发的任何配置里读取这些值」，§10.2 checklist 还要求「评审时打开源码核对，不接受『在配置文件里』」。但同一组范围值又写在附录 D 的 Schema 里（`ptzPar` 的 `[-170,170]`、`creepPar` 的 `[0.05,0.50]` 等）。

两处都有是好事——纵深防御，Schema 拦报文层、网关拦执行层。问题是 ICD 没说明白**它们必须同步**，也没有任何机制保证同步。**建议**在 `validate.py` 增加第 8 项检查：把网关源码里的范围常量与 Schema 里的 `minimum`/`maximum` 交叉比对，不一致即报错。这样"两份真值"就变成了"一份真值 + 一份自动校验的副本"。

### 一条正面结论

§10.1 列的**九条反例，我已逐条构造并对照附录 D 的五份 Schema 实测，全部被拦下（9/9）**；文档内的**六条示例报文也全部通过校验（6/6）**。`additionalProperties: false` 把「安全边界从约定变成机器强制」这个设计是真的成立的，不是纸面声明。

这一条要在评审时明确说出来。上面五条意见是在一个已经站得住的设计上做增量改进，不要让评审误以为 Schema 整体有问题。

### 6.2　C5：θ 取 60° 还是 67°

| | θ = 60°（两份文档现用） | θ = 67°（方案书 §4.1.3 自算） | 差 |
|---|---|---|---|
| 巡航像素密度 p（z=1, d=5 m） | 49.88 px | **43.51 px** | −6.37 |

| 所需变焦倍率 z_req | 2.406 | **2.758** | +0.35 |

影响面：

- **变焦余量被吃掉**：z_req 从 2.41 涨到 2.76，而镜头只有 3×。ICD §3.2 当初取 3 是"留余量"，按 67° 算余量只剩 8 %，基本没有了
- **路线标定规范要改**：ICD §3.2 硬约束「巡检位到表计目标的距离 d ≤ 6 m」与方案书 §5.3.3「每个观测位到其负责的表计目标的距离必须控制在 6 m 以内」都要改成 5 m
- **桩的标定素材要求要改**：ICD §9.2 与 §10.2 checklist 里的「桩上 d_max = 4.16 m 已写进标定素材要求」改为 3.63 m

θ 的真值最终由 ICD §9.2.3 的像素密度标定实测确定。但**在实测出来之前两份文档必须先统一口径**——现在的状态是镜头选型按一个数、像素密度推导按另一个数，而这两个数都出自方案书自己。

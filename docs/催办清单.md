### ~~`test_end_to_end_verify_cycle` 有 10 % 概率假红~~ ✅ 已修

实测 20 次复现 2 次，失败形态固定：

```
AssertionError: 状态机没走到 PACK，轨迹=['SUSPECT','HALT_REQ','AIM','ZOOM','CAPTURE','VERIFY']
```

**这是用例自己的竞态，不是产品缺陷。**失败那一轮系统完全正常——证据包照样落盘、
`verdict=READING_ABNORMAL`、`density_ratio=2.7446`、`verify_success` 为真。

根因是用例的**退出条件与断言对象之间没有因果关系**：

| | 谁产出 | 什么时候 |
|---|---|---|
| 退出条件 `rig.successful()` | **uploader** 线程写 `manifest.json` | 它自己配对完 before/after 就写，不等 mission |
| 断言对象 `PACK ∈ states` | **mission** 线程 `_st_verify` → `_goto(State.PACK)`（`fsm.py:547`） | 要等 mission 收到复核 DetectionEvent 并跑到那一拍 |

两条线各跑各的。机器一忙（日志里成片的 `单帧超出节拍 total_ms=245`），
mission 循环被饿着，uploader 先落盘 → 用例立刻 `rig.stop()` → mission 还没记下
VERIFY → PACK，`transitions` 里就缺这一项。

**修法（已做）**：`_Rig.wait_for_state` —— 找到 `good` 之后不立刻 `stop()`，而是有上限地等
`PACK` 进 `transitions`。产品代码没动，PACK 那条断言也留着：它验的是十状态机逐级走过。

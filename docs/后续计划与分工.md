## 零、先说清楚这份计划的前提

三条假设，如果和实际不符，对应的那一块要重排：

1. **硬件确定不来了**（原话"大概率不需要硬件"）。所以真机相关的任务
   ——固件串口补丁、F1 修复、真车联调——**全部移除**，不留支线。
   `drivers/real/` 那一层代码保留并继续由假小车验证：它是"硬件到位后能立刻
   接上"的证明，也是真机代码路径不腐烂的唯一保障。
2. **训练在你们自己的机器上跑**。我这边的沙箱下不到 Roboflow（要账号）
   和 PaddleX 直链（网络策略挡了 `bj.bcebos.com`），所以脚本与链路是验证
   过的，**权重一个都还没训**。
3. **周次是相对的**，按你们实际剩余时间对齐。四个阶段的**顺序**不能换，
   因为后一个阶段依赖前一个的产出。

## 二、四个人怎么分

分工按**接口边界**切，不按文件数切——这样四个人可以并行改，不会互相踩。
每人各自负责的目录写在括号里，**跨界的改动先在群里说一声**。

### 甲 · 识别模型（`training/`、`perception/detector/`）

把 L1 从"合成检测器"换成真模型。这是四条路里最独立的一条，可以第一天就开工。

| 任务 | 验收标准 |
|---|---|
| 下 `distribution_room`（2773 张，需注册免费 Roboflow 账号） | `prepare_dataset.py --check` 全绿 |
| 训巡航模型（小、快） | 验证集 mAP50 ≥ 0.70，单帧 ≤ 33 ms |
| 训复核模型（大、准） | 验证集 mAP50 优于巡航模型 ≥ 5 个点 |
| 导 ONNX 并接进链路 | 改 `perception.detector: yolo` 后 `run_all` 一轮不退化 |
| 合成集做增广，对比开与不开 | 一张表：只用公开集 vs 公开集+合成集的 mAP |

**注意两件事**：
- `DetectionEvent.model.name` 的枚举只有 `yolo11s` / `yolo11m`。要报别的名字
  得走 `validate.py` 的 `ALLOWED_DRIFT` 流程，**不许静默塞值**。
- **L1 权重要从公开数据集训，不要从合成集训**。合成数据补的是密度分层，
  不是纹理多样性——理由见 `training/README.md`。

### 乙 · 读数与精度（`perception/reading/`、`perception/segment/`、`tools/calibrate.py`）

把"读数准不准"从合成场景推进到有真实数据支撑。这是方案书表 2-2 的正式验收指标所在。

| 任务 | 验收标准 |
|---|---|
| 下 PaddleX 分割集，跑 `--from-paddlex` | **人眼看 `check/` 里的叠加图**确认掩膜没错位 |
| 在真实表盘图上跑 `read_pointer_gauge` | 误差表：真实图 vs 合成图，误差量级是否一致 |
| 用真实标注重训分割，对比针的 IoU | 现在是 0.182，看真实数据能提到多少 |
| 跑 `bench_models.py`，按像素密度分档 | 结论表：每一路该用哪个实现，**用数据说话** |
| 五点标定走一遍 `calibrate.py` | 至少一块表的标定表，进 `configs/` |

**核心指标**：指针读数误差 ≤ 0.5 % FS（方案书 §2.2）。
现在合成场景上是 0.05–0.14 % FS，**真实图上大概率会差一个量级**——
这个差距本身就是答辩时值得讲的东西，别藏。

### 丙 · 控制与系统可靠性（`mission/`、`tools/tune_pid.py`、`tools/fakecar.py`）

**硬件确定不来之后这个角色改过一次。**砍掉的是固件补丁、F1 修复、真车联调——
硬件不到，这三项就是空转。但下面这些**不依赖硬件**，而且课题名叫「测控系统」，
"控"那一半的证据全在这里：

| 任务 | 验收标准 |
|---|---|
| 跑 `tune_pid.py` 出阶跃响应曲线 | 超调 ≤ 5 %、调节时间 ≤ 0.8 s 的实测曲线图。**这是方案书 §11.1 明列的交付物** |
| 增益调度的对比演示 | 关掉调度后 3× 超调从 0.9 % 变 47.6 % 的两张图 |
| 假小车串口往返 | `fakecar.py` 起 PTY，`driver_mode: real` 跑通一轮 |
| **故障注入下的可靠性曲线**（新增） | 一张图：故障率 → 复核成功率 |
| **复核预算的调度实验**（新增） | 一张图：车速 / 路线长度 → N_max 与实际复核次数 |

后两项是现在**完全空白**的一块，而且正是"主动式"这个立论最需要的证据。

**可靠性曲线怎么做。**桩里本来就注入了真实故障率
（`configs/stub.yaml`：ACK 丢包 2 %、对焦失败 5 %、安全事件 0.05 次/分）。
把这几个数按倍数拉大重跑，画出"故障率 → 复核成功率"的曲线。
它回答的是评审一定会问的那个问题：**系统在会出错的环境里还能不能干完活。**
现在的答案只有一个点（默认故障率下 100 %），一个点画不成曲线。

**调度实验怎么做。**`N_max = ⌊(T_max − L/v)/T_r⌋` 现在只有单元测试，没有实验数据。
扫一遍车速与路线长度，把公式算出的 N_max 和实际完成的复核次数画在一起——
两条线贴合说明模型对，分叉的地方就是值得讲的发现。

> **如果丙确实要去做别的**：`tune_pid` 与增益调度对比归丙原本最熟的人，
> 其余归丁（他本来就管演示与指标汇总）。但**阶跃响应曲线不能省**——
> 那是交付物清单里点名要的东西。

### 丁 · 系统与交付（`gateway/`、`cloud/`、`tools/`、`docs/`）

保证前三个人的产出能被看见、能被演示、能写进报告。

| 任务 | 验收标准 |
|---|---|
| 三条安全演示做成脚本，一条命令一条 | 每条都能当场跑、有可见输出 |
| 三个显示面串起来演一遍 | `run_all` + `console` + `viewer --live` + 浏览器实时页 |
| 跑通 `export_rknn.py`（板子到了） | 导出 + 板上冒烟推理，INT8 掉点记录在案 |
| 量化校准集从 `evidence/` 取本场景图 | **不许用 COCO 之类通用图校准**，掉点会明显偏大 |
| 答辩材料 | PPT + 演示视频 + 指标表 |
| 补 0 覆盖率模块的用例 | `yolo.py`、`onnx_seg.py` 至少有接口回归 |

## 三、四个阶段

### 阶段一：把数据搞到手（约第 1 周）

四个人并行，**这一周的目标是消除所有"还没下数据"的阻塞**。

| 谁 | 做什么 |
|---|---|
| 甲 | 注册 Roboflow，下 `distribution_room`，跑通 `--to-yolo` |
| 乙 | 下 PaddleX 两个包（先 `wget` 试直链通不通），跑 `--from-paddlex` |
| 丙 | 跑 `tune_pid.py` 出阶跃响应曲线；搭故障注入实验的脚本 |
| 丁 | 把三条安全演示做成脚本；开始搭 PPT 骨架 |

**合流点**：`prepare_dataset.py --check` 全绿，两份数据集就位。
**这一周结束时如果数据还没到手，后面全部要顺延**，所以它排第一。

### 阶段二：把模型训出来（约第 2 周）

| 谁 | 做什么 |
|---|---|
| 甲 | 训两级 YOLO，导 ONNX，接进链路 |
| 乙 | 重训分割，跑真实表盘的读数误差 |
| 丙 | 假小车串口往返；跑出故障率 → 复核成功率的曲线 |
| 丁 | RKNN 导出链路；补 0 覆盖率模块的用例 |

**合流点**：`perception.detector: yolo` + `run_all` 跑一轮不退化于合成检测器。
**这是整个项目最关键的一次合流**——它证明"代码先行、模型后训"这条路走通了。

### 阶段三：调指标、出数据（约第 3 周）

| 谁 | 做什么 |
|---|---|
| 甲 | 消融实验：合成集增广开/关的对比表 |
| 乙 | `bench_models.py` 按密度分档的完整对比表；标定表进配置 |
| 丙 | 增益调度对比两张图；复核预算的调度实验 |
| 丁 | 板上部署；把所有指标汇总成一张验收表 |

**合流点**：方案书表 2-2 的每一项都有一个实测数字，**没测到的如实写"未测"**。

### 阶段四：收口与答辩（约第 4 周）

| 谁 | 做什么 |
|---|---|
| 全体 | 完整跑一遍演示流程，各自讲自己那部分 |
| 甲 | 模型部分的讲法：为什么四类模型、为什么这么选 |
| 乙 | 精度部分：像素密度论题 + 实测误差 |
| 丙 | 控制部分：PID 整定 + 安全边界 |
| 丁 | 系统部分：架构、部署、演示 |

**合流点**：一次完整彩排，**每个人都能回答"你那部分为什么这么做"**。

## 四、需要老师拍板的三件事

越早问越好，它们都会影响排期：

1. ~~固件没有串口怎么办~~ —— **已定：不上硬件。**固件评审的结论
   （`docs/底盘固件评审.md` 记的 9 处问题）仍然写进报告，作为"为什么这套
   方案要把驱动层抽象出来"的实证材料，但不再排开发工时。
2. **验收指标以哪一版为准。** 方案书表 2-2 的指标是按真实场景定的，
   我们现在只有合成场景的数。合成场景上的数算不算数，要说清楚。
3. **ICD 的两处缺口要不要正式补。** `mission_state` 没送到 perception
   （现在靠状态组合推断，已经因此出过一次静默失效）；`PTZ_RATE` 是增补
   指令但没写进冻结 Schema。补是对的，但要走评审。

## 五、风险与预案

| 风险 | 影响 | 预案 |
|---|---|---|
| ~~固件没串口~~ | ~~真机联调整块归零~~ | **已消解**：确定不上硬件，相关任务全部移除 |
| PaddleX 直链下不到 | 分割没有真实标注 | 合成掩膜顶上，但**要在报告里写明这个局限** |
| Roboflow 数据质量不够 | L1 训不出指标 | 合成集增广；或降级为"演示可用"并说明 |
| 真实表盘读数误差远大于合成 | 核心指标不达标 | **这是预期内的**，如实报告 sim-to-real gap 比硬凑数字好 |
| RKNN 掉点大 | 部署指标难看 | 用本场景图做量化校准；记录 FP16 与 INT8 两组数 |
| 时间不够 | 全线压缩 | 砍支线保主线：宁可少一个模型，不要少一条能演的闭环 |

**有一条纪律要贯穿始终**：**测不到的就写"未测"，测出来难看的就如实写。**
这个项目从头到尾的设计原则就是"证据不足时说不足，不猜"——报告里也一样。
评审最容易问倒人的不是"你这个指标为什么低"，而是"你这个数是怎么来的"。

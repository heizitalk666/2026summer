## 第二步：四步验证阶梯

按顺序跑。**每一步都有明确的预期输出，对不上就别往下走。**

### ① 接口一致性（10 秒）

```bash
python -m patrol.tools.validate
```

**你应该看到**（最后一行）：

```
PASS  Schema 5 份、正例 6 条、反例 11 条、内嵌副本一致、算例与预算全部自洽、
      网关常量与 Schema 同步（共 57 项）
```

中间会有几行灰色的「·」提示，那是已知的待评审项，不是错误。
**这一步不过，后面全是白费**——它验的是"代码和接口定义还对不对得上"。

### ② 看一眼虚拟配电室（20 秒）

```bash
python -m patrol.tools.viewer --demo-zoom --out out/
```

**你应该看到**：

```
  z=1  实测 bbox 宽 50.0 px，公式 p=49.8 px
  z=3  实测 bbox 宽 150.0 px，公式 p=149.5 px
已存 out/zoom_compare.png
```

打开 `out/zoom_compare.png`。**这张图是整个项目最直观的一幕**：同一块压力表，
巡航时只有 50 px（指针根本读不出来），3× 变焦后 150 px（刻度清清楚楚）。
"为什么要停车变焦"这个问题，这张图就是答案。

实测值和公式值吻合到 0.4 %——说明渲染器和光学公式是自洽的，不是各说各话。

### ③ 跑全部测试（约 1.5 分钟）

```bash
pytest -q
```

**你应该看到**：

```
501 passed, 1 skipped in 84.56s
```

跳过的那一条是需要真串口的。**一条都不该红。** 红了先看第五步的自查表。

### ④ 起全系统跑一轮巡检（5 分钟）

```bash
python -m patrol.tools.run_all --seconds 300 --console
```

`--console` 会同时开指令流水，你能**看着**车停下、云台转过去、变焦、再恢复：

```
[t=  80.7s] → 小车 ✓ 暂停 VERIFY_REQUEST                        1.5 ms
[t=  83.3s] → 云台 ✓ 转到 pan=+110.0° tilt=+2.7° zoom=1.00×     1.6 ms
[t=  84.1s] → 云台 ✓ 转速 pan=+3.6°/s tilt=+0.3°/s              0.5 ms
[t=  84.7s] → 云台 ✓ 转到 pan=+111.1° tilt=+2.7° zoom=2.59×     0.9 ms
[t=  86.9s] → 小车 ✓ 恢复巡航                                    0.9 ms
```

跑完出小结：

```
证据包 6 个，复核成功率 83.3 %（目标 > 85 %）

结论                      条数      平均Δconf        平均密度比
READING_ABNORMAL             2       0.3865       2.1883
READING_OK                   3       0.4696       2.1905
INCONCLUSIVE                 1       0.9697       0.0000
```

跑的过程中浏览器开 <http://127.0.0.1:8000/> 看云端台账，
「实时」那一页有指令流水和配电室俯视图。

#### 数字每轮都不一样，这是正常的

**别以为对不上就是坏了。**正常范围：

| 指标 | 正常范围 |
|---|---|
| 证据包 | 3–7 个 |
| 复核成功率 | 50 %–100 % |
| 平均密度比 | 1.8–2.4 |
| 真缺陷组 Δconf | > +0.25 |

**为什么会浮动**：桩里故意注入了真实的故障——ACK 丢包 2 %、对焦失败 5 %、
安全事件 0.05 次/分。一轮里出一两个 `INCONCLUSIVE` 完全正常，它有三种成因，
都是**系统按设计在工作**：

1. **融合层判互证冲突** → OCR 读到的量程和标定表对不上，交给人核对。
   这正是它该做的事
2. **AIM 状态超时** → 云台转动过程中目标出框，3 秒预算用完
3. **复核帧漏检** → 那一帧没检出目标，没有 after 快照，密度比记 0

打开 `evidence/<run_id>/<event_id>/fusion.json` 能看到每条结论的完整理由。

## 第三步：你这个角色的第一天

四步都过了，说明环境没问题。下面按分工各干各的
（分工书见 [`docs/后续计划与分工.md`](后续计划与分工.md)）。

### 甲 · L1 检测模型

```bash
# 1. 看要下哪些数据集、放到哪个目录
python -m training.prepare_dataset --list

# 2. 看合成数据长什么样（不需要下任何东西）
python -m training.gen_synthetic --n 40 --preview 8 --out training/datasets/demo
```

**产出**：`training/datasets/demo/check/` 里有 8 张核对图，框和掩膜画在图上。
终端还会打出像素密度分布（实测 40 帧：低于判据线 38 %、达标 62 %）。

**先用眼睛看几张核对图**——掩膜错位、类别号错位在任何数字上都看不出来，
只有画出来才看得见。

**下一步**：去 Roboflow 注册免费账号，下 `distribution_room`。

### 乙 · L2 分割与读数

```bash
# 1. 看读数精度现在是多少（这是你的核心指标）
pytest -q tests/test_reading_accuracy.py -s

# 2. 四路模型横向对比，按像素密度分档
python -m patrol.tools.bench_models --only reading
```

**产出**：按像素密度分档的读数误差表，实测长这样：

```
  像素密度        样本          几何 %FS     耗时ms     级联 %FS     耗时ms
  30–60 px    24            0.06      2.9          —        —
  120–180 px  24            0.10      3.0          —        —
```

「级联」那一列是「—」，因为分割权重还没训——这是**预期的**，不是坏了。
几何法现在 0.05–0.14 % FS，指标要求 ≤ 0.5 % FS。

**下一步**：下 PaddleX 分割集，跑真实表盘看误差差多少（**大概率差一个量级，
这是预期内的**）。

### 丙 · L3 未知异常检测

```bash
# 1. 正常样本集（不用下任何东西，这是三条路里最快能开工的）
python -m training.gen_synthetic --n 300 --out training/datasets/normal_patches

# 2. 训一版，看接口通不通（装不齐依赖会自动退回统计法，不会卡住你）
python -m training.train_anomaly --data training/datasets/normal_patches --backend auto
```

**产出**：`training/runs/anomaly/` 下的权重或 `baseline.json`，
终端打印误报/漏报与正常/异常均分。

**要理解的一点**：非监督，**只用"看起来正常"的样本**。现有的
`StatisticalAnomaly` 是在线学习 + 马氏距离，零权重、当场能跑、而且说得清
异常分来自哪个特征通道。你训出来的学习版要赢它才有意义——赢不了也是结论。

**下一步**：与统计法在**同一批样本**上比误报/漏报，再走 ONNX 导出与
`export_rknn.py` 的导出链路。

### 组长 · 系统与交付

```bash
# 1. 三个显示面一起看（开三个终端）
python -m patrol.tools.run_all --seconds 300      # 终端 1
python -m patrol.tools.console --push http://127.0.0.1:8000   # 终端 2
python -m patrol.tools.viewer --live              # 终端 3
# 浏览器 http://127.0.0.1:8000/ →「实时」页

# 2. 云台控制指标：PID 阶跃响应与增益调度对比（方案书 §11.1 点名的交付物）
python -m patrol.tools.tune_pid --out out/pid --compare-gain-schedule

# 3. 三条安全演示（见 docs/操作步骤.md §7）
```

**产出**：一套能当场演的流程，外加 `step_response.png` / `pid_report.json`。
实测输出：

```
阶跃 12° @ zoom=1x  超调 3.0%  调节时间 0.901s  稳态 7.6 px  达标
阶跃 12° @ zoom=3x  超调 1.0%  调节时间 1.202s  稳态 8.3 px  达标
关掉增益调度 @ zoom=3x  超调 47.7%  调节时间 1.202s  稳态 2.2 px
  → 这就是 §6.3.2 说的：不做调度时控制量是所需值的 3 倍
```

**最后那一行是答辩时最有说服力的一组对比**：同样的 PID 参数，
只是不按变焦倍率缩放控制量，超调就从 1 % 变成 47.7 %。

## 第五步：出错自查表

| 你看到的 | 真正的原因 | 怎么修 |
|---|---|---|
| `requirements.txt: No such file` | 不在仓库根目录，或停在了已废弃的旧分支 | `cd` 回仓库根目录；`git checkout main && git pull` |
| `No module named patrol` | 不在仓库根目录 | `cd` 回到能看到 `patrol/` 的那一层 |
| `SyntaxError` 指向 `str \| None` | Python < 3.10 | 装 3.10 以上，重建 venv |
| `Address already in use` | 15001–15003 或 8000 被占 | 上一次的进程没退干净：`pkill -f patrol` 后重来 |
| `pip install` 卡住或超时 | 默认源慢 | `pip install -i https://pypi.tuna.tsinghua.edu.cn/simple -r requirements.txt` |
| 预览窗口打不开 | 没有显示器（服务器 / WSL） | **不用管**，`viewer` 会自动转存图模式；也可换 `opencv-python-headless` |
| `rapidocr` 装不上 | 可选依赖 | **不用管**，OCR 那一路会自动降级，全链路照常跑通 |
| `pytest` 里 e2e 偶发红 | 机器负载高，端到端对时序敏感 | 单独重跑一次 `pytest -q tests/test_e2e_stub.py`；连续两次红才是真问题 |
| 一轮里有 `INCONCLUSIVE` | 多半正常 | 看上面「数字每轮都不一样」那节的三种成因 |
| 中文在图上显示成方框 | 系统没装中文字体 | 不影响功能；Linux 装 `fonts-wqy-zenhei` 即可 |
| `git push` 被拒 | 别人先推了 | `git pull --rebase origin main` 再推 |

# 架构说明

## 一句话

四个进程通过四条 JSON 接口通信，所有硬件访问经由四个抽象基类，桩与真机由
一个配置开关切换——**桩上验证过的逻辑在真机上同样成立**，整个无硬件并行
开发方案建立在这个前提上。

## 分层

```
┌─ cloud/ ─────────────── FastAPI + SQLite + 网页台账／人工复核／模型版本
│        ▲ HTTP（默认）或 MQTT 元数据 + HTTPS PUT 文件
│
├─ 四个节点进程 ────────────────────────────────────────────────
│                    IF-1 DetectionEvent
│   perception ─────────────────────────▶ mission
│        ▲                                   │ IF-2 ControlCommand (REQ/REP)
│        │                                   ▼
│        └──── IF-3 StatusReport ────────  gateway ──▶ 执行器
│                （PUB/SUB，一发多收）          │
│   uploader ◀── IF-1 + IF-3 ─────────────────┘
│        │ IF-4 EvidencePackage
│        ▼ 落盘 evidence/<run_id>/<event_id>/
│
├─ drivers/ ──── IChassis / IPTZ / ICamera / ILocalizer 四个抽象基类
│      factory.py 是全仓库唯一的 driver_mode 分支点
│   ├── stub/  桩：主动注入真机上会出现的麻烦
│   └── real/  串口 / V4L2
│
└─ scene/ ────── 虚拟配电室（只在 stub 模式加载，真机模式不读）
```

## 四个进程的职责与边界

| 进程 | 职责 | 碰执行器 | 崩了会怎样 |
|---|---|---|---|
| `perception` | 一级巡航检测、二级复核推理、L2 读数、L3 异常 | 否 | 心跳还在（mission 发），但没有事件，状态机停在 CRUISE |
| `mission` | 复核状态机、抑制、预算调度、云台 PID | 否，只发指令 | 心跳断，网关看门狗 1.5 s 后下发 RESUME，车走完路线 |
| `gateway` | 白名单、参数范围、状态冲突、安全否决、心跳看门狗 | **是，唯一出口** | 一切运动指令无人接收，车按底盘安全层自行处置 |
| `uploader` | 证据包组装、断点续传、云端上报 | 否 | 证据包堆在本地，网络恢复后补传 |

`perception` 与 `mission` 之间不经过网关，因为二者都不产生执行器动作。
**所有指向底盘和云台的动作只有 `gateway` 一个出口**，这是安全边界第一层的
物理保证。

## 四条接口

| 编号 | 名称 | 方向 | 传输 | 频率 |
|---|---|---|---|---|
| IF-1 | `DetectionEvent` | perception → mission / uploader | PUB/SUB | 10 Hz 巡航 + 按需复核 |
| IF-2 | `ControlCommand` / `CommandAck` | mission → gateway | REQ/REP | 事件驱动 + 5 Hz 心跳 |
| IF-3 | `StatusReport` | gateway → 所有人 | PUB/SUB | 20 Hz + 安全事件插播 |
| IF-4 | `EvidencePackage` | uploader → 云端 | HTTP/MQTT | 每次复核一包 |

选 REQ/REP 给 IF-2 是有意的：**它强制每条指令必须有回执**。网关不回 ACK 会
阻塞 mission——宁可状态机卡在超时上被日志记下来，也不要指令悄悄丢失。

`event_id` 是串起四份 Schema 的主键。同一次复核里的 DetectionEvent、
ControlCommand、StatusReport、EvidencePackage 全部携带同一个 `event_id`，
事后按它过滤日志就能拿到完整的一条时间线。

## 传输地址

默认 `tcp://127.0.0.1`，不是 ICD 原文的 `ipc://`——`ipc` 在 Windows 上不可用，
而组里的笔记本多半是 Windows。ICD §1.2 已预留这个口子。地址在
`configs/system.yaml` 的 `bus` 段，真机可切回 `ipc`。

## 桩与真机的切换

```yaml
driver_mode: stub     # stub | real
```

除 `patrol/drivers/factory.py` 外，全仓库任何其他文件出现
`if mode == "stub"` 都算违反约定，评审时会检查。桩和真机的差异必须全部
封在实现类里；一旦泄漏到业务代码，"桩上验证过的逻辑在真机上同样成立"这个
前提就不成立了。

## 虚拟配电室

`scene/` 是无硬件条件下跑通全链路的支点。它不是"随便画点东西让程序不崩"：

- **像素密度公式在渲染图上是真的成立的。**变焦实现为视场角收缩
  `hfov(z) = 2·arctan(tan(θ₀/2)/z)`，于是针孔投影自动满足
  `p = W·D·z/(2·d·tan(θ₀/2))`。实测 5 m 处表盘 z=1 时 50.0 px、z=3 时
  150.0 px，公式值 49.8 / 149.5，吻合到 0.4 %。
- **每个目标的真值只用于渲染与打分，感知侧拿不到。**读数算法必须真的从
  像素里解算角度。`World.Target.priors`（量程、扫过角，标定阶段可知）与
  `.truth`（当前读数，只有"上帝"知道）是分开的两个属性。
- **桩主动制造麻烦。**停车延迟 1.5–2.5 s（**故意超出 2.0 s 预算**）、2 % 指令
  丢包、安全事件与急停注入、5 % 对焦失败、到位抖动、定位失锁。在桩上调不通
  的状态机，真机上一定崩。

## 三层安全机制

| 层 | 限制什么 | 落在哪 |
|---|---|---|
| 协议层 | 识别模块**能表达什么** | `gateway/limits.py` 的白名单 + Schema 的 `additionalProperties: false` |
| 网关层 | 表达的内容**是否被接受** | `gateway/checks.py` 五项校验，范围值硬编码在源码 |
| 优先级层 | 被接受的指令**是否被执行** | 底盘安全层，独立于网关，可否决任何上层指令 |

三级独立生效，任一级单独失效不导致边界被突破。协议里不存在转向角、轮速、
扭矩、制动力、目标速度这类量——AI 侧没有任何字段可以直接指定车怎么动。

**越界一律拒绝而不截断。**截断会让 AI 侧的 bug 静默通过：发了 5 m 的
`CREEP_FORWARD` 被截成 0.5 m 照常执行，联调时看不出问题，等到某次截断逻辑
失效就出事。

## 关键数据流：一次复核

```
perception  检出 conf=0.41、p=49.8px  → is_suspect=true, rule=CONF_BAND
            生成 event_id，此后全程携带
   │ IF-1
   ▼
mission     CRUISE →(连续3帧确认)→ SUSPECT →(五条抑制+预算检查)→ HALT_REQ
            发 PAUSE ─IF-2→ gateway ─→ chassis.pause()
            等 chassis.state == STOPPED（区分 STOPPING！）
            → AIM   云台 PID 速率闭环，像素偏差进 ±20 px 带并保持 3 拍
            → ZOOM  按需变焦 z = clip(z·p_target/p, 1, 3)，等 focus=LOCKED
            → CAPTURE
   │ IF-3 状态组合（STOPPED + zoom≥1.8 + at_target + LOCKED）
   ▼
perception  连拍 3 帧挑最清晰的 → 二级模型 → L2 读数
            发 stage=VERIFY 的 DetectionEvent，**携带同一个 event_id**
   │ IF-1
   ▼
mission     VERIFY → PACK → RESUME → CRUISE
uploader    按 event_id 配对 before/after → 算增益 → 组装 manifest → 上传
```

## 已知的接口缺口

实现过程中发现两处 ICD 的问题，已在代码注释里标注、待 D3 评审：

1. **§4.5 两句话自相矛盾。**「心跳超时期间拒绝一切 `issued_by = MISSION_FSM`
   的指令」与「恢复条件：心跳恢复且连续 3 条正常」——心跳本身就是
   MISSION_FSM 发的，按前一句拒掉之后后一句永远不可能满足，看门狗一旦触发
   就死锁。实测确实如此。实现里放行了 HEARTBEAT，建议 ICD 补一句"HEARTBEAT
   除外"。
2. **没有接口把 `mission_state` 送到 perception。**§7.2 写着 CAPTURE"走
   ICamera"、VERIFY"走 perception"，但四条接口里没有一条能让 mission 通知
   perception"该复核了"。实现里靠 IF-3 的状态组合推断（底盘停稳 + 变焦拉起
   + 云台到位 + 对焦锁定，这四条同时成立只在复核时发生），建议 IF-3 的
   `watchdog` 块增补一个可选的 `mission_state`，由网关从心跳里透传。

## Schema 版本

`1.1.0`。相对 ICD 冻结的 1.0.0 有五处增补，全部是"新增可选字段/枚举值"
（按 ICD 冻结规则只需次版本号 +1、通知即可）：

| 增补 | 来源 |
|---|---|
| `detections[].quality` | A4 四项质量指标 |
| `trigger_rule` 增 `QUALITY_LOW` | A4 |
| `files[].role` 增 `VERIFY_FRAME_AUX` | A3 条件式辅视角 |
| `files[].role` 增 `CRUISE_VIDEO` | B3 任务书要求证据含视频 |
| `snapshot.multiview_spread` | A3 三视角读数极差 |

`tools/validate.py` 第 6 项会逐路径列出 `schemas/` 与附录 D 的差异，**只放行
登记在 `ALLOWED_DRIFT` 里的条目**，未登记的差异一律判失败——目的是让偏移
可见，而不是掩盖它。

# 设计思想

这份文档回答的是"为什么这样做"，而不是"怎么做"。怎么做看 `docs/架构说明.md`
和代码注释。

## 一、把"没有硬件"变成可测的试验台

硬件全部未到位时最容易走的路是"先写个能跑的简化版，硬件到了再重写"。那条
路的问题不在于工作量，在于**简化版上验证过的东西到真机上一条都不作数**，
四周的周期实际压缩成两周。

这里走的是另一条：直接把最终架构搭起来，只让最底下一层跑桩。前提是桩必须
诚实到能替真机说话，为此做了三件事。

**渲染必须服从物理。**虚拟配电室不是画着好看的，它按针孔模型投影，变焦实现
为视场角收缩 `hfov(z) = 2·arctan(tan(θ₀/2)/z)`。于是像素密度公式
`p = W·D·z/(2·d·tan(θ₀/2))` 不是事后拿来核对的，而是投影的**推论**。实测
5 m 处 15 cm 表盘 z=1 时 50.0 px、z=3 时 150.0 px，公式值 49.8 / 149.5。
这条等价关系有专门的测试盯着（`test_pixel_density.py`），它挂了说明投影实现
错了，后面所有精度指标都不用看。

**真值只用于打分，不许喂给算法。**场景知道每块表的指针角度，但读数算法只
拿到一张图和一个检测框，必须真的从像素里把角度解算回来。`Target.priors`
（量程、扫过角——标定阶段本来就录入的合法信息）与 `Target.truth`（当前读数）
是分开的两个属性，后者只有渲染器和测试脚本碰。

有一条测试专门防作弊：同一张图配不同的量程先验，读数必须按比例缩放而角度
不变。算法一旦偷看真值，这条立刻挂。还有一条更根本的：**误差必须随像素密度
退化**。如果哪天这条曲线变平了，那不是算法变好了，是它开始作弊了。

**桩要主动制造麻烦。**停车延迟 1.5–2.5 s，下限与 `HALT_REQ` 的 2.0 s 预算只差
500 ms，上限**故意超出预算**——预算是均值意义上的，超出预算但不超时的情况
必须在桩上出现，否则没人会去测"复核偶尔慢一点会怎样"。2 % 的指令丢包意味着
一轮巡检大概率丢一条，状态机扛不住就会在联调时翻车。急停保留 5 % 的概率，
因为它是唯一不能自恢复的安全事件，这条路径不在桩上跑过，真机上第一次按急停
就是现场事故。

## 二、安全边界要能当场演示，不能只是声明

任务书的硬约束是"AI 不得直接控制车辆底层执行机构"。声明这一条很容易，让它
可验证才是设计。

**协议层让 AI 无法表达。**白名单只有六条指令，参数里不存在转向角、轮速、
扭矩、制动力、目标速度。配合 Schema 的 `additionalProperties: false`，任何人
想往协议里塞一个转向角，报文当场就过不了校验——**安全边界由此从"约定"变成
"机器强制"**，不需要靠代码评审去发现。

**网关层的范围值硬编码在源码里。**`gateway/limits.py` 不 import config，不接受
任何运行时参数。ICD §10.2 的评审 checklist 写得很直白：「评审时打开源码核对，
不接受『在配置文件里』」。

**越界拒绝而不截断。**这一条最容易写反。截断看起来更"健壮"，实际上是让 AI 侧
的 bug 静默通过：发了 5 m 的 `CREEP_FORWARD` 被截成 0.5 m 照常执行，联调时
一切正常，等到哪天截断逻辑本身失效就出事。拒绝会立刻暴露在日志里。

**`checks` 字段让校验本身可观测。**每条 ACK 逐项列出五层校验各自的结果，
`PASS` / `FAIL` / `SKIP`。这个字段看起来冗余，但它让"网关到底有没有在校验"
这件事可以被抽查——如果某一项长期是 `SKIP`，说明那层校验根本没接上。

**看门狗让车走完路线，不是让车停住。**AI 进程崩了的时候，车停在配电室通道
中间比走完路线回充电位更麻烦。巡检路线本身是标定过的安全路径，底盘沿着它走
不需要 AI 参与。真正需要立刻停车的情况由底盘安全层处理，那条通路不经过 AI
也不经过网关。

## 三、每个数字都要能追到它的来源

方案书的立论是一条推导链：

```
0.5 % FS 精度要求
  → 误差传递（指针尖端 ±1 px、表盘中心 ±1 px，方和根合成）
  → 表盘半径 r ≥ 60 px，即直径 p_min = 120 px
  → 巡航 5 m 处只有 50 px，不够
  → 所需变焦 z_req = 120/50 = 2.4，取 3×
  → 3× 到顶时反解距离上限 d_max ≈ 6.2 m，取 6 m
```

代码里这条链的每一环都是可执行的，不是注释：`optics.pixel_density` 是公式本身，
`scale.error_budget` 复现方案书表 6-1（120 px → 0.650 % FS，150 px → 0.577 %
FS），`validate.py` 第 3 项复核全部标定算例，`test_pixel_density.py` 验证渲染
图上量出来的像素宽度确实等于公式值。

**误差预算里承认了不达标。**方案书 §6.1.5 自己写着：120 px 时合成误差 0.65 %
FS，略超 0.5 % 指标。这不是要藏起来的事——它恰恰说明 120 px 是**触发阈值**
而不是**精度阈值**，实际部署要靠复核后更高的像素密度获得余量。实测下来（43 次独立标定）：5 m / 3× / 149.5 px 时基本误差中位 **0.455 % FS**
（理论预算 0.578 %）、线性度 0.302 % FS，两项达标；**重复性 0.309 % FS 没达标**
（限值 0.3，43 次里 29 次不合格）。像素密度再高误差还会继续降，但重复性这一项
不是靠提高密度能解决的——它与指针指向强相关，逐条见
[`deliverables/组长-系统/README.md`](../deliverables/组长-系统/README.md)。

**这一条也不藏。**本节讲的就是「误差预算里承认不达标」，那么实测出来不达标的那一项
更没有理由粉饰。

## 四、控制部分要有真的被控对象

云台 PID 如果对着一个"赋值即到位"的假云台整定，出来的参数、超调量、调节
时间全是假的，答辩一问就穿。所以 `ptz_stub` 实现了角速度上限、角加速度
240 °/s²、齿隙 0.05°、到位抖动 0.15°、变焦耗时 800–1400 ms、5 % 对焦失败。

在这个被控对象上整定的结果有两条值得记下来：

**方案书表 6-4 的 Kp=0.40 是初值不是整定结果。**实测该参数下闭环时间常数约
2.75 s，4 s 内根本进不了 ±20 px 带（稳态还差 141 px）。临界比例度法测得
Kcr = 7.0、Tcr = 1.12 s，齐格勒-尼科尔斯给出 Kp=4.20 但超调 11 % 偏激进
（Z-N 的已知特性），回退到 Kp=3.0 / Ki=1.2 / Kd=0.12 后 z=1 与 z=3 下三项
指标全部达标。这条已固化成一条会失败的测试，免得有人照抄初值就上机。

**增益调度的必要性有了实证。**关掉调度后 z=3× 超调 42.7 %，开着是 1.0 %。
方案书 §6.3.2 说这一条可以现场演示作为对比——现在它是 `test_servo.py` 里
一条会失败的测试，谁"顺手"把调度删了当场就红。

## 五、把踩过的坑留在代码里

实现过程中有几个 bug 是设计层面的，不是笔误。它们的成因写在了对应的代码
注释里，因为**下一个人很可能会以同样的方式再写错一次**：

- **读数算法的采样环包含了刻度带**，指针经轴帽与刻度连成一个连通域，PCA 被
  环形刻度拉成各向同性，方向完全失效。改用极坐标展开 + 逐环角质心取中位数。
- **手写射线采样按整数像素取点**，相邻 0.5° 的射线在半径 45 px 处只差 0.39 px，
  会采到同一批像素，覆盖率曲线被量化成台阶，亚度级质心被台阶花纹带偏 2° 以上。
  必须用 `warpPolar` 的双线性插值。
- **看门狗拒绝心跳导致死锁**，见架构说明的"已知接口缺口"。
- **伺服在没喂过样本时报"到位"**，`_e_filt` 初值是 0，AIM 状态一拍就过，
  PID 根本没跑过——审计日志里一条 `PTZ_RATE` 都没有才发现。
- **巡航云台姿态写成"相对车体左转 90°"**，车一折返云台就背对柜列，返程段
  检出直接归零。正确的表达是"对准 map 系的某个方位"，由 `pan = 方位 − yaw`
  实时折算。
- **`event_id` 只在 `is_suspect` 为真时携带**，而复核态的报文里触发判据已经
  不成立（变焦后像素密度达标了），于是这条最关键的报文丢了主键，证据包的
  增益指标全是零。ICD §2.2 说得很清楚：它是串起四份 Schema 的主键，全程都要带。

后面这一批是端到端联调时才暴露的。共同点是**单元测试全绿、单看每一层都对**，
只有把四个进程真正连起来跑才会现形——这也是为什么必须有一条端到端测试
（`test_e2e_stub.py`），而且它必须重建四进程的拓扑，不能图省事共用一套驱动：

- **四个进程各建一套驱动，于是有四个互不相干的虚拟世界。**只有网关那套收得到
  指令，感知那套的云台永远停在开机位。症状是复核期间 AIM 三十拍一个检出都
  没有，而日志里云台明明"已经对准柜列"。见架构说明"桩模式下物理世界住在哪个
  进程"。
- **俯仰通道多了一个负号。**方位收敛得好好的，俯仰却在发散：巡航 tilt=2.0°
  而表计与相机等高，2° 的初始偏差被正反馈一路放大，约 1 s 后目标垂直出框。
  链路上唯一的症状是"检出突然归零"，极易误判成检测器漏检或渲染出错。
  **成因是测试只覆盖了方位通道**——现在两条通道的符号各有一条用例钉着。
- **纯速率闭环打不过反馈滞后。**感知 10 Hz + 任务 10 Hz + 总线往返 ≈ 200 ms，
  云台 60 °/s 在这段时间里已经扫过 12°，大角度指向必然冲过头。这不是 PID 参数
  的问题，再怎么整定都躲不掉——正确的做法是把几何上完全已知的那部分做成前馈。
- **云台一动 IoU 跟踪就断链。**帧间框平移一百五十像素以上，重叠归零，跟踪分配
  新 id，按 id 找反馈量一个都对不上。真机上同样会发生。
- **复核报文比状态机早到。**perception 判断"该复核了"靠的是 IF-3 的状态组合，
  这个条件在 mission 还在 ZOOM/CAPTURE 时就成立了；而每拍只保留最后一条 IF-1，
  随后的巡航报文把它覆盖掉，状态机进到 VERIFY 时已经没了。
- **`event_id` 被"上一次复核的尾巴"抢走。**复核结束、变焦还没退回广角的那
  800–1400 ms 里触发判据照样成立，于是新起一个事件，它的 `before` 快照记的是
  变焦后的样子，像素密度比一算只剩 1.01——把复核最核心的那条指标做废了。
- **把被抑制的可疑事件也算进复核成功率。**同目标冷却、同巡检位已测过这些是
  抑制规则**正常工作**，不是复核失败。都打成 INCONCLUSIVE 的话分母被撑大，
  实测把成功率从 100 % 拉到 60 %，指标彻底失去意义。
- **判决优先级把 L3 排在二级读数前面。**L3 是非监督的，对一块读数明确且在正常
  带内的表报异常多半是光照或视角引起的重构误差。排错的后果是整轮压力表全被判
  成 `UNKNOWN_ANOMALY`，读数通路等于白做。现在读数优先，L3 的意见转成
  `needs_human_review`——这也正合 ICD §3.1「L3 输出只允许进人工复核队列」。
- **伪终端默认带回显。**假小车收到自己发出的状态帧，判成 UNKNOWN_TYPE 再回一条
  REJ，REJ 又被回显，链路瞬间被自激的帧刷满。症状是"指令发出去没反应，状态帧
  却一直正常上报"。真串口没有这一条，是伪终端仿真特有的坑。
- **回执把被回执的 seq 塞进了帧头。**协议里 `ACK,<seq>,<result>` 的那个 seq 是
  被回执的指令号，帧自己的 seq 是底盘的计数器，两个是不同的东西。写混了上位机
  永远对不上句柄，表现为每条指令都超时，而链路上明明看得到 ACK 在飞。
  **这个 bug 是被"两侧共用同一份编解码 + 一条往返用例"抓出来的**，这正是把
  协议实现单独成模块的理由。

### 两个独立选定的常数，可以在没人察觉的情况下互相锁死

这一条是收尾复跑时才抓到的，值得单独讲，因为它的**失效方式**比它本身更有
代表性。

ICD §7.2 说复核阶段"走 perception"，但四条冻结接口里没有任何一条把
`mission_state` 送到感知节点。所以感知只能看 IF-3 的状态组合去**猜**状态机
走到哪一步了。原来的猜法是：

```
底盘停稳 + 变焦 ≥ verify_zoom_min(1.8) + 云台到位 + 对焦锁定
```

而状态机下发的变焦是按需算的：`target_zoom = clip(p_target / p_before, 1, 3)`。
两个常数在两个文件里各自独立定，凑在一起就锁死了：`p_target = 120 px` 时，
只有巡航期像素密度 ≤ 120/1.8 = **66.7 px** 的目标才会被放大到 1.8× 以上。

> **巡航期看得比 66.7 px 还清楚的目标，复核 100 % 会在 VERIFY 超时。**

注意这个失效模式有多别扭：**目标离得越近、看得越清楚，复核越是必然失败**。
而且全程一行报错都没有——状态机在 VERIFY 干等到超时，证据包里留下一个
`density_ratio = 0` 的 INCONCLUSIVE，看上去和"这次没看清"没有任何区别。
实测一轮 7 个证据包中一个。

改法是把判据从"绝对阈值"换成"和状态机同一个公式算出来的期望值"——
`zoom_for_density` 是共用的纯函数，两边喂同一个 `p`（就是感知自己刚写进
IF-1 的那个 `pixel_density_px`），算出来逐位相同。

**修的过程本身又踩了两次**，都记在 `tests/test_verify_due.py` 里：

1. 第一版把判据换成"云台离开巡航姿态"。但 AIM 的第一步就是一条
   `PTZ_SET(pan=目标方位, zoom=1.00)` 的前馈粗对准——那一刻四条全中，
   而判据一命中就立刻发报文并清掉 `event_id`。于是复核报的是放大**之前**
   的画面，密度比 1.07。证据包看起来完好，复核其实没发生。
2. 第二版把期望倍率在铸主键时记一次。但复核是可以重试的：第一次因对焦
   失败中止后 `event_id` 保留，状态机会在车又开近一点之后重来，重新算出
   的倍率更小，而感知还攥着第一次那个更大的值——又是一次干等超时。
   对齐的时机必须是"发出 `is_suspect=true` 的那一帧"，因为状态机就是拿
   那条报文算的；被抑制的帧状态机根本不理，拿它们刷新会把期望值改成一个
   状态机从未用过的数。

三次都是同一类错误：**两个模块对同一件事各自持有一份推断，而没有任何机制
保证它们一致。**所以最后加了一条兜底——四条无歧义的条件稳定保持超过
`verify_grace_s` 而只有倍率对不上时，照发不误并打一条 WARN。

这条兜底的价值不在于它能修好什么，而在于它把**静默失效变成了有声失效**。
复核质量差一点，是能在证据包的密度比里看出来的；而状态机干等到超时，
除非有人专门去比对两份日志的时间线，否则永远不会有人发现。

## 六、统计口径写进代码而不是写进脑子

`delta_conf` 对 `FALSE_ALARM` 是负值——复核把一个 0.41 的误检压到 0.05，
`Δconf = −0.36`，这是正常的，而且是**有价值的结论**：一级为了保召回把阈值
压到 0.25，必然带来误报，复核把它们消解掉正是这套方案的立论所在。

但如果统计时把它和真缺陷混在一起算均值，结果会接近零，看上去像复核完全没
起作用。ICD §6.4 特意警告过这一点，所以：`cloud/db.py` 的 `gain_stats()`
强制按 `verdict` 分组并单独给出真缺陷组的均值，`run_all` 的收尾报告和台账
网页上都印着这句提醒。**能写进代码的约定就不要只写进文档。**

## 七、多一路模型，就多一个会说错话的嘴

这一节讲的是加了四类模型协同之后学到的东西。完整的设计在
[`docs/多模型协同.md`](多模型协同.md)，这里只留三条**教训**。

### 举证责任的方向决定了系统好用还是难用

接 OCR 互证的第一版，判据是"OCR 读到的数字对不上先验量程 → 判标定错配"。
听上去无懈可击。端到端一跑，**复核成功率从 100 % 掉到 28.6 %**。

原因是 OCR 在 120 px 的表盘上会把 `0.4` 读成 `4`、`1.2` 读成 `12`——小数点
是第一个丢掉的东西。于是"对不上"满地都是。

改对之后的判据是：**只有当读到的数字自身构成一套自洽的等距刻度、且这套
刻度指向另一个量程时，才判冲突。**举证责任从"证明这些数字对不上先验"变成
"证明这是**别的**表"。噪声凑不出自洽刻度，真看错表则一定凑得出。

一般化一下：**新加的一路证据，默认应当只能让结论更保守，不能让结论翻盘。**
要让它有权翻盘，它得先拿出比原结论更强的证据。这条对任何"多模型投票"的
设计都成立。

### "证据不足"和"冲突"是两件事

`CrossCheck.agree` 是三态而不是布尔：

```
True   一致    → 佐证，置信度上抬
False  冲突    → 反证，压过读数，交人
None   证据不足 → 既不佐证也不反证，只让结论保守一档
```

第一版只有两态，把"没读清楚"当成"读出来不一样"。代价是 71 个百分点的复核
成功率。**二值化一个本质上三态的判断，是这类系统里最贵的偷懒。**

### 两条通路说的是同一件事，用的却是两套词

几何法报 `CLOSED`/`OPEN`，位置指示牌印的是 `ON`/`OFF`。直接比字符串，于是
"几何法 CLOSED vs 位置牌 ON"——两路其实完全一致——被判成互相矛盾，一轮里
6 个开关证据包全部误标。

这个 bug 不会崩、不会让任何测试变红，只会让指标悄悄变难看。**跨模块比较
任何离散量之前，先过一次归一化**，哪怕两边的词表看起来"显然一样"。

### 附带的一条：默认值要用数据定，不要用直觉定

分割那一路，学习法与几何法在本项目的表盘上**持平而慢 2.3 倍**
（`tools/bench_models.py` 按像素密度分档实测）。所以默认关掉它。

"新做的东西默认开着"是很自然的冲动，但每加一路模型都要付出代价——推理时间、
一个会失效的新组件、一条新的"两路不一致怎么办"的规则。**答不上"它把什么
指标变好了多少"的那一路，就该关掉。**这个工具的存在本身就是一个立场：
多模型协同不是"模型越多越好"。

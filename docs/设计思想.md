# 设计思想

这份文档回答的是"为什么这样做"，而不是"怎么做"。怎么做看 `docs/架构说明.md`
和代码注释。

## 一、把"没有硬件"变成可测的试验台

硬件全部未到位时最容易走的路是"先写个能跑的简化版，硬件到了再重写"。那条
路的问题不在于工作量，在于**简化版上验证过的东西到真机上一条都不作数**，
四周的周期实际压缩成两周。

这里走的是另一条：直接把最终架构搭起来，只让最底下一层跑桩。前提是桩必须
诚实到能替真机说话，为此做了三件事。

**渲染必须服从物理。**虚拟配电室不是画着好看的，它按针孔模型投影，变焦实现
为视场角收缩 `hfov(z) = 2·arctan(tan(θ₀/2)/z)`。于是像素密度公式
`p = W·D·z/(2·d·tan(θ₀/2))` 不是事后拿来核对的，而是投影的**推论**。实测
5 m 处 15 cm 表盘 z=1 时 50.0 px、z=3 时 150.0 px，公式值 49.8 / 149.5。
这条等价关系有专门的测试盯着（`test_pixel_density.py`），它挂了说明投影实现
错了，后面所有精度指标都不用看。

**真值只用于打分，不许喂给算法。**场景知道每块表的指针角度，但读数算法只
拿到一张图和一个检测框，必须真的从像素里把角度解算回来。`Target.priors`
（量程、扫过角——标定阶段本来就录入的合法信息）与 `Target.truth`（当前读数）
是分开的两个属性，后者只有渲染器和测试脚本碰。

有一条测试专门防作弊：同一张图配不同的量程先验，读数必须按比例缩放而角度
不变。算法一旦偷看真值，这条立刻挂。还有一条更根本的：**误差必须随像素密度
退化**。如果哪天这条曲线变平了，那不是算法变好了，是它开始作弊了。

**桩要主动制造麻烦。**停车延迟 1.5–2.5 s，下限与 `HALT_REQ` 的 2.0 s 预算只差
500 ms，上限**故意超出预算**——预算是均值意义上的，超出预算但不超时的情况
必须在桩上出现，否则没人会去测"复核偶尔慢一点会怎样"。2 % 的指令丢包意味着
一轮巡检大概率丢一条，状态机扛不住就会在联调时翻车。急停保留 5 % 的概率，
因为它是唯一不能自恢复的安全事件，这条路径不在桩上跑过，真机上第一次按急停
就是现场事故。

## 二、安全边界要能当场演示，不能只是声明

任务书的硬约束是"AI 不得直接控制车辆底层执行机构"。声明这一条很容易，让它
可验证才是设计。

**协议层让 AI 无法表达。**白名单只有六条指令，参数里不存在转向角、轮速、
扭矩、制动力、目标速度。配合 Schema 的 `additionalProperties: false`，任何人
想往协议里塞一个转向角，报文当场就过不了校验——**安全边界由此从"约定"变成
"机器强制"**，不需要靠代码评审去发现。

**网关层的范围值硬编码在源码里。**`gateway/limits.py` 不 import config，不接受
任何运行时参数。ICD §10.2 的评审 checklist 写得很直白：「评审时打开源码核对，
不接受『在配置文件里』」。

**越界拒绝而不截断。**这一条最容易写反。截断看起来更"健壮"，实际上是让 AI 侧
的 bug 静默通过：发了 5 m 的 `CREEP_FORWARD` 被截成 0.5 m 照常执行，联调时
一切正常，等到哪天截断逻辑本身失效就出事。拒绝会立刻暴露在日志里。

**`checks` 字段让校验本身可观测。**每条 ACK 逐项列出五层校验各自的结果，
`PASS` / `FAIL` / `SKIP`。这个字段看起来冗余，但它让"网关到底有没有在校验"
这件事可以被抽查——如果某一项长期是 `SKIP`，说明那层校验根本没接上。

**看门狗让车走完路线，不是让车停住。**AI 进程崩了的时候，车停在配电室通道
中间比走完路线回充电位更麻烦。巡检路线本身是标定过的安全路径，底盘沿着它走
不需要 AI 参与。真正需要立刻停车的情况由底盘安全层处理，那条通路不经过 AI
也不经过网关。

## 三、每个数字都要能追到它的来源

方案书的立论是一条推导链：

```
0.5 % FS 精度要求
  → 误差传递（指针尖端 ±1 px、表盘中心 ±1 px，方和根合成）
  → 表盘半径 r ≥ 60 px，即直径 p_min = 120 px
  → 巡航 5 m 处只有 50 px，不够
  → 所需变焦 z_req = 120/50 = 2.4，取 3×
  → 3× 到顶时反解距离上限 d_max ≈ 6.2 m，取 6 m
```

代码里这条链的每一环都是可执行的，不是注释：`optics.pixel_density` 是公式本身，
`scale.error_budget` 复现方案书表 6-1（120 px → 0.650 % FS，150 px → 0.577 %
FS），`validate.py` 第 3 项复核全部标定算例，`test_pixel_density.py` 验证渲染
图上量出来的像素宽度确实等于公式值。

**误差预算里承认了不达标。**方案书 §6.1.5 自己写着：120 px 时合成误差 0.65 %
FS，略超 0.5 % 指标。这不是要藏起来的事——它恰恰说明 120 px 是**触发阈值**
而不是**精度阈值**，实际部署要靠复核后更高的像素密度获得余量。实测下来：
5 m / 3× / 149.5 px 时基本误差 0.469 % FS（理论预算 0.578 %），三项指标全部
达标；像素密度再高误差还会继续降。

## 四、控制部分要有真的被控对象

云台 PID 如果对着一个"赋值即到位"的假云台整定，出来的参数、超调量、调节
时间全是假的，答辩一问就穿。所以 `ptz_stub` 实现了角速度上限、角加速度
240 °/s²、齿隙 0.05°、到位抖动 0.15°、变焦耗时 800–1400 ms、5 % 对焦失败。

在这个被控对象上整定的结果有两条值得记下来：

**方案书表 6-4 的 Kp=0.40 是初值不是整定结果。**实测该参数下闭环时间常数约
2.75 s，4 s 内根本进不了 ±20 px 带（稳态还差 141 px）。临界比例度法测得
Kcr = 7.0、Tcr = 1.12 s，齐格勒-尼科尔斯给出 Kp=4.20 但超调 11 % 偏激进
（Z-N 的已知特性），回退到 Kp=3.0 / Ki=1.2 / Kd=0.12 后 z=1 与 z=3 下三项
指标全部达标。这条已固化成一条会失败的测试，免得有人照抄初值就上机。

**增益调度的必要性有了实证。**关掉调度后 z=3× 超调 42.7 %，开着是 1.0 %。
方案书 §6.3.2 说这一条可以现场演示作为对比——现在它是 `test_servo.py` 里
一条会失败的测试，谁"顺手"把调度删了当场就红。

## 五、把踩过的坑留在代码里

实现过程中有几个 bug 是设计层面的，不是笔误。它们的成因写在了对应的代码
注释里，因为**下一个人很可能会以同样的方式再写错一次**：

- **读数算法的采样环包含了刻度带**，指针经轴帽与刻度连成一个连通域，PCA 被
  环形刻度拉成各向同性，方向完全失效。改用极坐标展开 + 逐环角质心取中位数。
- **手写射线采样按整数像素取点**，相邻 0.5° 的射线在半径 45 px 处只差 0.39 px，
  会采到同一批像素，覆盖率曲线被量化成台阶，亚度级质心被台阶花纹带偏 2° 以上。
  必须用 `warpPolar` 的双线性插值。
- **看门狗拒绝心跳导致死锁**，见架构说明的"已知接口缺口"。
- **伺服在没喂过样本时报"到位"**，`_e_filt` 初值是 0，AIM 状态一拍就过，
  PID 根本没跑过——审计日志里一条 `PTZ_RATE` 都没有才发现。
- **巡航云台姿态写成"相对车体左转 90°"**，车一折返云台就背对柜列，返程段
  检出直接归零。正确的表达是"对准 map 系的某个方位"，由 `pan = 方位 − yaw`
  实时折算。
- **`event_id` 只在 `is_suspect` 为真时携带**，而复核态的报文里触发判据已经
  不成立（变焦后像素密度达标了），于是这条最关键的报文丢了主键，证据包的
  增益指标全是零。ICD §2.2 说得很清楚：它是串起四份 Schema 的主键，全程都要带。

## 六、统计口径写进代码而不是写进脑子

`delta_conf` 对 `FALSE_ALARM` 是负值——复核把一个 0.41 的误检压到 0.05，
`Δconf = −0.36`，这是正常的，而且是**有价值的结论**：一级为了保召回把阈值
压到 0.25，必然带来误报，复核把它们消解掉正是这套方案的立论所在。

但如果统计时把它和真缺陷混在一起算均值，结果会接近零，看上去像复核完全没
起作用。ICD §6.4 特意警告过这一点，所以：`cloud/db.py` 的 `gain_stats()`
强制按 `verdict` 分组并单独给出真缺陷组的均值，`run_all` 的收尾报告和台账
网页上都印着这句提醒。**能写进代码的约定就不要只写进文档。**
